# Phase 11 – AI Complaint Analysis: Setup, Safety and Limits

The AI complaint analysis module supports two modes:

1. **Groq AI analysis:** Uses the Groq API with the `openai/gpt-oss-120b` model.
2. **Rule-based fallback:** Automatically generates analysis when Groq is unavailable, disabled, incorrectly configured, or returns an invalid response.

The fallback ensures that AI failures never prevent students from submitting complaints.

**Important architecture decision:** AI analysis is integrated into the existing `complaint-api` Appwrite Function. We do not create a separate `ai-analysis` function.

## What it does

After a student submits a complaint, the complaint is stored first. The server then analyses its title and description asynchronously and stores the results in the **AI Summaries** (`ai_summaries`) table.

The analysis includes:

- A short summary.
- A suggested category.
- The department responsible for that category.
- A suggested priority (Low / Medium / High / Urgent).
- Sentiment or tone.
- Relevant keywords.
- A confidence value.
- A one-line explanation.
- Whether the result was generated by AI or the rule-based fallback.
- Model information and error details, when applicable.

**Access and permissions**

- Department staff can view AI analysis for complaints belonging to their department.
- Administrators can view AI analysis for complaints they are authorized to manage.
- Students must never see AI analysis, confidence scores or internal recommendations.

**The AI only suggests.** It must not automatically change complaint status, priority, category, department or assignment.

Authorized staff and administrators should be able to:

- Mark an analysis as reviewed.
- Dismiss an analysis.
- Apply the suggested priority. This action must create an internal note identifying the person who applied it.
- Run analysis again when permitted.

Only an **administrator** can move a complaint to another category or department based on the AI suggestion. This action must be authorized and audited.

If analysis fails or the AI provider is unavailable, authorized staff should see the reason and be able to run the analysis again when permitted. Each complaint must have a maximum of 10 analysis attempts.

## How it is built (and why it is safe)

### Actual project architecture

```text
Browser
   |
   v
complaint-api
   |
   |-- Checks authentication and permissions
   |-- Stores the complaint first
   |-- Starts another asynchronous execution
   |   of the same complaint-api function
   |
   v
Internal AI execution
   |
   |-- Verifies INTERNAL_AI_SECRET
   |-- Runs analyzeComplaint()
   |-- Reads complaint and available categories
   |-- Redacts personal information
   |
   v
Groq API (HTTPS)
   |
   |-- Model: openai/gpt-oss-120b
   |
   v
Validates AI response
   |
   v
Stores result in ai_summaries
   |
   v
Authorized staff / administrators
```

**Important:** The internal AI analysis is another asynchronous execution of the existing `complaint-api` function. There is no separately deployed `ai-analysis` function.

### Provider credentials and API key protection

- The Groq API key is stored only in the Appwrite `complaint-api` function environment variables.
- It is not included in the React application, frontend `.env`, database records or browser requests.
- It must never appear in application logs or Git repositories.
- The Appwrite server API key and `INTERNAL_AI_SECRET` must also remain secret.
- The browser must never contact Groq directly.

Unlike the original separate-function design, the AI provider key is stored in `complaint-api`. This is the architecture used by the current project.

### Internal execution security

The internal AI action is protected by `INTERNAL_AI_SECRET`.

The function checks the supplied secret using a timing-safe comparison before accepting the internal action.

Normal browser requests must not be able to execute the internal AI analysis action by supplying a complaint ID alone.

The `COMPLAINT_API_FUNCTION_ID` environment variable must contain the ID of the existing `complaint-api` function.

### Personal data protection

Before sending complaint text to Groq, the server uses the redaction utility.

The provider should receive only the complaint title and description, truncated to the configured limits (150 / 2,000 characters), with personal information replaced by placeholders.

Examples:

- Email addresses → `[email]`
- Phone numbers → `[phone]`
- Roll numbers or ID numbers → `[roll number]`
- Student names → `[name]`
- Links → appropriate placeholders

The provider must not intentionally receive:

- Student user ID.
- Complaint ID.
- Student email or roll number.
- Profile information.
- Attachments.
- Private location information.
- Authentication credentials.

The category names are also provided so the model can select from available categories.

Redaction is pattern-based and best-effort. It cannot guarantee removal of every personal detail written in free text. Students should be advised not to include sensitive personal information in complaint descriptions.

### AI response validation

The AI response is untrusted and must be validated before being stored.

The existing validation module must enforce:

- Valid JSON object structure.
- Category selection only from the categories supplied to the model.
- Valid department association.
- Priority limited to Low, Medium, High and Urgent.
- Valid sentiment values.
- Valid confidence score.
- Text sanitization and length limits.
- Ignoring unexpected fields such as `status`, `assignedTo` or other unauthorized instructions.

Complaint text must be treated as untrusted data. The prompt instructs the model not to follow instructions contained inside complaint descriptions.

Even if a model follows malicious instructions, it must not be able to make unauthorized changes to complaints. It can only produce a suggestion that passes server-side validation.

### Error handling, rate limits and outages

The provider adapter handles:

- HTTP 429 rate limits.
- HTTP 5xx provider errors.
- Request timeouts.
- Invalid credentials.
- Refused requests.
- Empty responses.
- Invalid or unreadable responses.

Retry behavior:

- One retry for timeouts.
- One retry for HTTP 5xx errors.
- One retry for rate limits when `Retry-After` is 5 seconds or less.
- No retry for invalid credentials or ordinary refused requests.

The current provider code has a maximum timeout of 25,000 milliseconds (25 seconds), even if `AI_TIMEOUT_MS` is configured to 30,000.

When AI analysis fails, the rule-based fallback should generate the analysis and store a clear explanation.

A failed or unstartable AI analysis must never prevent complaint submission or affect the student's confirmation.

### No unauthorized decisions

The AI only generates suggestions.

Applying a suggested priority or moving a complaint to another category or department must be a separate, authorized and audited human action.

The server must enforce department permissions and administrator-only reassignment.

## 1. Update the database (existing tables)

If the database schema has not already been updated, run:

```powershell
$env:APPWRITE_API_KEY="<key>"; npm run db:setup -- --no-seed
```

The setup process adds the required `ai_summaries` columns:

- `source`
- `reason`
- `attempts`
- `reviewStatus`
- `reviewedBy`
- `reviewedByName`
- `reviewedAt`

It may print warnings for two enum columns that require the new `urgent` value. Update them manually in Appwrite Console:

**Databases → Your Database → Tables → Column → Edit**

- `complaints.priority` → `low, medium, high, urgent`
- `ai_summaries.priority` → `low, medium, high, urgent`

New installations should already contain the correct values.

Also verify:

- `ai_summaries` has Row Security enabled.
- Students cannot read AI summaries.
- Only authorized server-side operations and administrators/staff can access the relevant analysis data.

Do not recreate existing tables unnecessarily.

## 2. Configure Groq in the existing `complaint-api` function

Do not create a separate `ai-analysis` function.

Open:

**Appwrite Console → Functions → complaint-api → Settings → Variables**

Configure the following variables:

| Variable | Value |
|---|---|
| `AI_PROVIDER` | `groq` |
| `AI_ENABLED` | `true` |
| `GROQ_API_KEY` | Your Groq API key (secret) |
| `AI_MODEL` | `openai/gpt-oss-120b` |
| `AI_BASE_URL` | `https://api.groq.com/openai/v1` (optional; this is the default) |
| `AI_TIMEOUT_MS` | `30000` (actual code maximum: 25000 ms) |
| `APPWRITE_API_KEY` | Appwrite server API key with the required database and function-execution permissions (secret) |
| `DATABASE_ID` | Your existing Appwrite database ID |
| `INTERNAL_AI_SECRET` | Your internal execution secret (secret) |
| `COMPLAINT_API_FUNCTION_ID` | ID of the existing `complaint-api` function |

**Important configuration rules:**

- `GROQ_API_KEY` must be marked secret.
- `APPWRITE_API_KEY` must be marked secret.
- `INTERNAL_AI_SECRET` must be marked secret.
- Never expose these values in frontend code.
- The Appwrite API key must have the required permissions for database operations and function executions.
- `COMPLAINT_API_FUNCTION_ID` must reference the same deployed `complaint-api` function.

When `AI_ENABLED=false` or Groq is not configured, the rule-based fallback should remain available.

Redeploy the existing `complaint-api` function whenever its source code changes.

No additional Appwrite function or deployment is required for AI analysis.

## Verify against the real project

The following verification steps should be completed against the deployed application.

1. **Verify fallback mode:** Temporarily disable AI using `AI_ENABLED=false` and submit a complaint as a student. The complaint must still be created, and the `ai_summaries` record should show `source = fallback`, `model = rule-based-fallback` and an explanation.

2. **Verify Groq mode:** Enable Groq and submit another complaint. The AI summary should be generated and stored in `ai_summaries`. A successful record should contain:
   - `source = ai`
   - `model = groq:openai/gpt-oss-120b`
   - `status = completed`
   - `errorMessage = null`

3. **Verify personal data redaction:** Submit a test complaint containing a fake name, email and phone number. Confirm that the provider receives placeholders instead of the original personal information, wherever provider request inspection is available.

4. **Verify student restrictions:** As a student, check complaint pages and My Complaints. They must not display AI analysis or internal recommendations.

5. **Verify department restrictions:** As staff from a different department, attempt to access a complaint that does not belong to your department. The backend must deny access.

6. **Verify staff actions:** Test Mark as Reviewed, Dismiss and Apply Suggested Priority. Applying priority must update the complaint and create an internal note identifying the responsible person.

7. **Verify administrator actions:** Test Move to Suggested Category and department reassignment. These actions must be available only to administrators and must be audited.

8. **Verify reruns:** Confirm that authorized staff/admin users can run analysis again, students cannot trigger reruns, and the backend enforces a maximum of 10 attempts per complaint.

9. **Verify provider failure:** Use an invalid test key or disable AI temporarily. The complaint must still be created and the analysis must use the rule-based fallback with a meaningful explanation.

10. **Verify browser security:** In the browser's Network tab, confirm that no request goes directly to Groq and no API key appears in browser requests or responses.

## Cost and abuse controls

The intended behavior is:

- One initial provider call per complaint.
- Re-analysis only when authorized staff or administrators request it.
- Maximum 10 analysis attempts per complaint.
- Students cannot request re-analysis.
- A running analysis must not be duplicated.
- Completed analysis should be reused unless an authorized rerun is requested.

These limits must be enforced by the backend, not only by hiding frontend buttons.

Configure spending limits or usage alerts in the Groq account.

## Known limitations

- Personal data redaction is pattern-based and cannot guarantee removal of every sensitive detail.
- The fallback uses keyword matching and may not understand every language or unusual complaint description.
- AI suggestions depend on the categories and departments available in the database.
- AI recommendations may be incorrect and require human review.
- Analysis runs asynchronously. If processing takes longer than the frontend polling period, the result may appear after a page reload.
- Groq availability, model access and rate limits can change.
- The current architecture stores AI provider credentials in `complaint-api`, rather than isolating them in a separate function.
- The AI provider integration has been tested successfully, but staff/admin interface actions and all security scenarios still require end-to-end verification.
- Staff cannot independently reassign a complaint to another department. Only administrators can perform this action.
